# File ownership

codebuild decides what it may write by who owns each file. `codebuild plan` shows the decision for every file before anything is written.

| Path | Owner | Behavior |
|---|---|---|
| `**/*_gen.go`, `**/*_gen_test.go` | codebuild | Regenerated on every build. |
| `internal/<domain>/service.go` | you | Created once with explicit methods that call the repository, never touched again. |
| `internal/<domain>/service_<method>.go` | you | Created when the generated handler needs a service method you do not have yet; never touched again. |
| `internal/<domain>/auth_service.go`, `auth_service_<method>.go` | you | With authentication: created once in the account domain; missing `AuthService` methods get new files. See [authentication.md](authentication.md). |
| `cmd/api/main.go`, `cmd/migrate/main.go`, `cmd/accounts/main.go` | you | Created once. `cmd/accounts` exists only with authentication. |
| `internal/platform/config/config.go` | you | Created once. |
| `internal/platform/database/database.go` | you | Created once; it calls the generated `Connect`. |
| `AGENTS.md`, `.gitignore`, `.gitattributes`, `.dockerignore`, `Dockerfile`, `.github/workflows/ci.yml` | you | Created once. `.gitattributes` keeps LF line endings even when Git converts them on Windows. |
| `specs/*.go` | you | Never written by codebuild. |
| `migrations/NNNN_<name>.up.sql`, `.down.sql` | you after creation | Created once when the schema changes; existing migrations are never modified. |
| `migrations/codebuild.snapshot.json` | codebuild | The schema produced by all generated migrations. Commit it. |
| `codebuild.json` | you | Created when missing; rewritten only by `--change-dialect`. |
| `go.mod` | you | See below. |

## Plan actions

| Action | Meaning |
|---|---|
| `create` | The file does not exist and will be written. |
| `update` | A generated file changed and will be regenerated. |
| `unchanged` | The generated content is identical. |
| `skip` | A user-owned file already exists and is left alone. |
| `conflict` | A generated file lost its header, or a migration with the same name exists. Nothing is written until it is resolved. |
| `stale` | A generated file that the specs no longer produce. It is kept. |
| `delete` | A stale generated file removed because `--prune` was given. |

## Edited generated files

Every generated file starts with:

```go
// Code generated by codebuild. DO NOT EDIT.
```

If you remove that line, codebuild treats the file as yours and refuses to overwrite it: `build` exits with code 6 and lists the file. Move your changes to a file you own (for example `service.go` or a new file in the same package) and delete the generated file, or restore the header to let codebuild regenerate it.

## Business logic

Handlers call `Service`, and `Service` calls the repository. `service.go` is written once with one explicit method per operation, for example:

```go
func (s *Service) Create(ctx context.Context, in CreateInput) (User, error) {
	return s.repo.Create(ctx, in)
}
```

Add rules, transactions (`database.InTx` and `Repository.WithTx`) and calls to other repositories there. Nothing is promoted implicitly: if a method is not on `Service`, the handler does not compile, so a rule cannot be bypassed by accident.

When a spec change makes the handlers need a method that `Service` lacks, for example the listing of a new relation, codebuild parses the non-generated files of the package with `go/parser` and writes only the missing methods, each in a new file such as `service_list_org_users.go`. It never edits a file that exists. If such a file already exists without the method, the plan warns and you add the method by hand.

`internal/app/routes_gen.go` creates services with `NewService(db *sql.DB)`, so a service can build any repository it needs without changing that signature. A domain that needs dependencies from outside the database, or routes of its own, can be listed in `manualWiring` in `codebuild.json`; codebuild then leaves it out of the generated wiring and you register it in `cmd/api/main.go`.

Extra queries go in files you own inside the domain package, as methods on `*Repository`.

## Migrations and the snapshot

On each build codebuild compares the schema derived from the specs with `migrations/codebuild.snapshot.json`. When they differ it writes the next migration (`0002_alter_users.up.sql` and `.down.sql`) and updates the snapshot. It warns about destructive changes, such as dropped tables or columns, and about drops and additions that may be a rename, so you can edit the new migration before applying it.

- Never edit a migration that was already applied; change the spec instead.
- You may edit a migration that has not been applied yet, for example to turn a drop and an add into a rename.
- If SQL files exist but the snapshot is missing, codebuild stops with exit code 7 instead of guessing.
- Hand-written migrations with higher numbers are respected when numbering new ones, but codebuild does not know their effect on the schema.

## go.mod

codebuild edits `go.mod` with `golang.org/x/mod/modfile` and only to:

- add the driver of the dialect and, on Go 1.26, `github.com/google/uuid`, when they are missing (existing versions are never downgraded);
- raise the `go` directive when you authorized it for a project below Go 1.26.

It never runs network commands; run `go mod tidy` afterwards.

## Pruning

Removing a spec or adding `noroutes` leaves generated files behind as `stale`. `codebuild build --prune` deletes them, after re-checking the generated header. User-owned files in the same directory stay.
